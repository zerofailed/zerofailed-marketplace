# Upgrading GitVersion from v5 to v6

`ZeroFailed.Build.Common` installs GitVersion `5.8.0` by default. A repo moves to v6 when it sets
`$GitVersionToolVersion` (or `ZF_BUILD_GITVERSION_TOOL_VERSION`) to a `6.x` version, for example:

```powershell
# .zf/config.ps1
$GitVersionToolVersion = '6.8.2'
```

The standardised `GitVersion.yml` that our repos use (the file generated by the pr-autoflow mechanism) is
written for v5. It does not work with v6 without changes. Some of the problems stop the build. Others
change the generated versions without a warning.

## Symptom

The `GitVersion` task fails with an error similar to:

```
WARN [..] An error occurred:
Failed to parse 1.0 into a Semantic Version
ERROR: Command exited with code 1. { dotnet-gitversion /output json /nofetch /config $GitVersionConfigPath }
```

Fixing only this error is **not enough**. The build then succeeds, but the versions it produces are
different from v5 (see [Results](#results)).

## The standardised v5 configuration

```yaml
mode: ContinuousDeployment
branches:
  master:
    regex: ^main
    tag: preview
    increment: patch
  dependabot-pr:
    regex: ^dependabot
    tag: dependabot
    source-branches:
    - develop
    - master
    - release
    - feature
    - support
    - hotfix
next-version: "1.0"
```

Some repos use a `main:` key without a `regex:` line instead of `master:`. The value of `next-version`
is different in each repo.

## The equivalent v6 configuration

This configuration gives the same versions as the v5 configuration above:

```yaml
mode: ContinuousDelivery
branches:
  main:
    label: preview
    increment: Patch
  release:
    mode: ContinuousDelivery
  feature:
    mode: ContinuousDelivery
  hotfix:
    mode: ContinuousDelivery
  unknown:
    mode: ContinuousDelivery
  dependabot-pr:
    regex: ^dependabot
    label: dependabot
    increment: Inherit
    source-branches:
    - develop
    - main
    - release
    - feature
    - support
    - hotfix
next-version: "1.0.0"
```

Keep the repo's own `next-version` value, but give it three parts (`"0.1"` becomes `"0.1.0"`). When the
repo already has release tags, `next-version` has no effect, and you can remove it.

## Required changes

| # | v5 | v6 | Why | If you do not change it |
|---|---|---|---|---|
| 1 | `next-version: "1.0"` | `next-version: "1.0.0"` | v6 parses `next-version` as a strict three-part SemVer. | The build fails: `Failed to parse 1.0 into a Semantic Version`. |
| 2 | `tag:` | `label:` | v6 renamed the branch property. | **No error.** v6 ignores `tag`, so `main` builds lose the `preview` label and get release-style versions (for example, `1.2.4` instead of `1.2.4-preview.2`). |
| 3 | `mode: ContinuousDeployment` | `mode: ContinuousDelivery` | v6 changed what the mode names mean. v5 `ContinuousDeployment` (a pre-release number that increases with each commit) is v6 `ContinuousDelivery`. v6 `ContinuousDeployment` treats every commit as a release and removes the pre-release label. | **No error.** `main` builds get release-style versions. |
| 4 | *(not needed)* | `mode: ContinuousDelivery` on `release`, `feature`, `hotfix` and `unknown` | In v5, the root `mode` applied to all branches. In v6, these built-in branch configurations set `mode: ManualDeployment`, which overrides the root `mode`. | **No error.** Each commit on these branches gets the **same** `SemVer` (for example, `1.2.4-foo.1`). Only the build metadata changes (`+5`). A second pre-release package from the same branch then has a version that already exists. |
| 5 | *(not needed)* | `increment: Inherit` on `dependabot-pr` | In v6, a custom branch configuration needs an explicit `increment: Inherit` to take the increment from its source branch. | **No error.** Dependabot branches get the version of the last release tag (for example, `1.2.3-dependabot.4` instead of `1.2.4-dependabot.4`), which is lower than the version already released. |
| 6 | `master:` with `regex: ^main` | `main:` with no `regex` | The built-in v6 `main` configuration already matches `^master$\|^main$`. A separate `master` key duplicates it. | It still works, but the configuration is harder to read. If you rename the key, also change `master` to `main` in the `source-branches` list of `dependabot-pr`. |

## Results

These results come from a test repository with a `1.2.3` tag on `main`, run with GitVersion `5.8.0` and
`6.8.2` (`SemVer` output):

| Branch | v5 (standard config) | v6 (rows 1 and 2 only) | v6 (all changes) |
|---|---|---|---|
| `main` | `1.2.4-preview.2` | `1.2.4` | `1.2.4-preview.2` |
| `feature/foo` | `1.2.4-foo.5` | `1.2.4-foo.1` | `1.2.4-foo.5` |
| `dependabot/nuget/bar` | `1.2.4-dependabot.4` | `1.2.3` | `1.2.4-dependabot.4` |
| `release/1.3` | `1.3.0-beta.2` | `1.3.0-beta.1` | `1.3.0-beta.4` |
| `hotfix/oops` | `1.2.4-beta.5` | `1.2.4-beta.1` | `1.2.4-beta.5` |
| `spike/thing` | `1.2.4-spike-thing.4` | `1.2.4-spike-thing.1` | `1.2.4-spike-thing.4` |

On `release/*` branches, v6 counts the pre-release number in a different way from v5. The number still
increases with each commit, so each build still has a unique version.

To check a repo's configuration before you change the tool version, run both versions against it and
compare the output:

```powershell
dotnet tool install GitVersion.Tool --version 6.8.2 --tool-path ./.gv6
./.gv6/dotnet-gitversion /output json /nofetch /config ./GitVersion.yml
```

## Output variables that v6 removed

The `GitVersion` task puts every output property in `$script:GitVersion` and in `GITVERSION_<name>`
environment variables. v6 does not output these properties:

- `NuGetVersion`, `NuGetVersionV2`
- `NuGetPreReleaseTag`, `NuGetPreReleaseTagV2`
- `LegacySemVer`, `LegacySemVerPadded`
- `BuildMetaDataPadded`, `CommitsSinceVersionSourcePadded`

v6 adds `VersionSourceDistance`, `VersionSourceIncrement` and `VersionSourceSemVer`.

Look for these names in the repo's `.zf/config.ps1`, its custom tasks and its CI/CD workflows. Also check
that `GitVersionComponentForBuildNumber` does not name a removed property. Use `SemVer`,
`MajorMinorPatch`, `PreReleaseTag` (`preview.2`), `PreReleaseLabel` (`preview`) or `PreReleaseNumber`
(`2`) instead.

> **ZeroFailed.Build.PowerShell:** its `PublishPowerShellModules` task uses `NuGetPreReleaseTag` to
> decide if a build is a pre-release and to make the module's `Prerelease` value. With v6 this value
> is empty, so the task treats **every** build as a stable release: it publishes pre-release builds
> without a pre-release label, and to repositories that have `BlockPreReleaseVersions` set. Do not use
> GitVersion v6 in a repo that publishes PowerShell modules until that extension supports v6.
